# 🌱 Mindi

**MDN을 읽고, 진짜 이해했는지 확인해주는 웹 학습 친구.**

웹 개발 개념을 자기 말로 설명하면, MDN 원문에서 저작한 **루브릭**을 기준으로 어떤 요소가 비어 있고 무엇이 잘못되어 있는지 되돌려 줍니다. 정답을 바로 알려주지 않고, 세 단계 힌트로 스스로 고치게 돕습니다.

서버가 채점하지 않습니다. 브라우저가 임베딩과 검색을 하고, 페이지를 연 사람의 컴퓨터에서 실행 중인 Ollama가 진단을 만듭니다.

- **배포 주소**: `[결정 필요 — GitHub Pages 주소를 여기 적으세요]`
- **제품 약속**: [PRD.md](PRD.md)
- **판정 기준**: [data/rubrics/](data/rubrics/) · **지식 원본**: [data/source.md](data/source.md)

## 처음 오셨다면 — 이 순서로

이 도구는 **여러분의 컴퓨터가 진단을 생성**합니다. 페이지가 열리는 것과 진단이 나오는 것은 다른 일입니다.

### ① 배포 주소를 열고 다루는 개념을 확인합니다

현재 점검할 수 있는 개념은 **HTTP**와 **CSS 박스 모델** 둘입니다. 그 밖의 질문은 답을 지어내지 않고 범위 밖임을 밝힙니다.

### ② Ollama를 실행하고 모델을 준비합니다

```bash
ollama pull qwen3:4b
```

### ③ 첫 방문에는 임베딩 모델을 내려받습니다 (약 200MB)

진행률이 왼쪽 **설정과 기록**에 표시됩니다. 한 번 받으면 브라우저 캐시에 남습니다. ONNX 런타임(WASM) 자산도 함께 받으므로 첫 로드는 시간이 걸립니다.

### ④ 배포 주소에서 호출하려면 CORS를 허용해야 합니다 — 안 하면 반드시 실패합니다

이 단계를 건너뛰면 화면에 답이 안 나옵니다. 로컬(`localhost:5173`)에서는 Ollama가 기본으로 허용하므로 잘 되다가, 배포 주소에서만 막힙니다.

```bash
setx OLLAMA_ORIGINS "https://내계정.github.io"
```

Windows에서는 위 명령 후 **Ollama를 완전히 종료했다가 다시 실행**해야 반영됩니다.
(작업 표시줄 아이콘 오른쪽 클릭 → Quit. macOS/Linux는 `launchctl setenv OLLAMA_ORIGINS "..."` 또는 `OLLAMA_ORIGINS="..." ollama serve`)

설정하지 않으면 Ollama가 preflight 요청에 **403**을 돌려줍니다. 앱은 이 상황을 감지해 무엇을 해야 하는지 화면에 적어 줍니다.

### ⑤ 개념을 고르고 시작합니다

입구가 둘입니다.

- **읽어 보기** — MDN 원문 그대로. 문단마다 왼쪽에 키워드가 있고, **가리기**를 누르면 본문만 흐려지고 키워드는 남습니다. 남은 낱말로 내용을 떠올려 보세요. 이걸로 끝내도 됩니다
- **설명해 보기** — 자기 말로 설명하면 무엇이 비었는지 알려 줍니다. 정답은 주지 않고 힌트를 세 번까지 줍니다

범위 밖 질문과 "그냥 답 알려주세요"는 근거를 밝히고 거절합니다.

## 설계 — 루브릭이 채점하고, 검색은 세 자리에만 있습니다

이 제품의 핵심은 **루브릭 채점**입니다. 그러면 임베딩과 검색은 왜 있는가. 답하지 않으면 검색은 장식이 됩니다.

### 먼저, 검색을 쓰지 않는 곳

> **요소별 상태 판정에는 검색을 쓰지 않습니다. 판정은 오직 루브릭으로만 합니다.**

검색 결과로 채점하면 같은 설명이 검색에 따라 다르게 채점됩니다. 판정 일관성은 "범용 챗봇 + 프롬프트 한 줄"이라는 대체재 대비 **유일한 구조적 우위**라 양보하지 않습니다.

### 검색이 실제로 일하는 자리

| # | 자리 | 루브릭이 못 하는 이유 | MVP에서 |
| --- | --- | --- | --- |
| ① | **범위 판정과 거절** | 루브릭은 *이미 고른 개념*의 요소 목록이라 자료 밖을 모른다 | **필수** |
| ② | **오개념 교정의 출처** | 루브릭은 판정 기준이지 설명이 아니다. 왜 틀렸는지가 없다 | **필수** |
| ③ | Hint 3의 문단 선택 | 학습자마다 막힌 지점이 달라 고정 앵커로는 덜 맞는다 | 이득 작음 |

③은 개념 2개·청크 47개 규모에서 고정 앵커 대비 이득이 크지 않습니다. **MVP에서 검색을 정당화하는 것은 ①과 ②입니다.** 과장하지 않고 그대로 적습니다.

### 두 층의 판정

| | 1층 (Mindi) | 2층 (LLM-as-a-Judge) |
| --- | --- | --- |
| 채점 대상 | **학습자의 설명** | **Mindi의 진단** |
| 기준 | 루브릭 | 근거성 |
| 출력 | 요소별 4상태 + 오개념 | grounded / cited / refusal / relevant / complete / verdict |

### 처리 순서

```
설명 입력
  ↓ 임베딩 + 하이브리드 검색 (코사인 + BM25, RRF)
  ↓ 범위 판정 ── 밖/정답요구 → 거절 (근거 표시)
  ↓ 3-a 진단 호출 ── 루브릭 + 학습자 발화만. 원문 없음
  ↓ 3-b 교정 호출 ── 모순이 잡혔을 때만. 여기서만 원문
  ↓ 종료 판정 ── 달성 / 확인 / 교정 / 힌트 1~3 / 소진
  ↓ 2층 판정
```

## 실험 기록

한 번의 실행에서는 **변수 하나만** 바꾸고 나머지 조건과 입력 순서를 유지합니다.
**실패한 결과도 지우지 않습니다.** 다음 수정이 무엇을 보존해야 하는지 알 수 없게 되기 때문입니다.

### 실험 1 — 범위 판정 구간을 실측으로 확정

| 항목 | 내용 |
| --- | --- |
| 바꾼 변수 | 범위 판정 임계값: 단일 0.55 → 3구간 (안 ≥0.65 / 확인 0.58~0.65 / 밖 <0.58) |
| 고정 조건 | 청크 47개, EmbeddingGemma 768d, 탐침 14건 |

| 무리 | 유사도 범위 |
| --- | --- |
| 자료 안 6건 | 0.705 ~ 0.806 |
| 경계 2건 | 0.573 ~ 0.640 |
| 자료 밖 6건 | 0.453 ~ 0.553 |

**관찰한 근거**: 분리 여유 0.152로 두 무리가 겹치지 않습니다. **PRD 7.2 ①의 주장이 실측으로 성립합니다.**
그런데 애초의 0.55는 틀린 값이었습니다 — "깃 머지랑 리베이스 차이"(0.553)가 범위 안으로 통과합니다.
일반 RAG 챗봇의 약한 근거 임계값을 그대로 가져온 결과였고, 측정하지 않았으면 몰랐을 오류입니다.
또한 단일 임계값으로는 경계 사례를 처리할 수 없어, **원칙 7(저확신 시 단정하지 않고 확인 질문)을 범위 판정에도 적용**했습니다.

**결정: 채택.** `npm run probe` 가 회귀 검사입니다. 표본 14건이므로 청크가 바뀌면 다시 재야 합니다.

### 실험 2 — 루브릭 인용의 정확성 검사를 기계화

| 항목 | 내용 |
| --- | --- |
| 바꾼 변수 | 인용 검사 방식: 앞 4어절 대조 → 인용 전체 대조(공백 제거 후) |

**관찰한 근거**: 느슨한 검사에서는 2건만 걸렸고, 전체 대조로 바꾸자 **제가 쓴 인용 4건이 원문과 다름**이 드러났습니다.

| 요소 | 무엇이 틀렸나 |
| --- | --- |
| RB-A3 | 괄호 안 `(requests)`를 표시 없이 생략 |
| RB-A6 | `(데이터 스트림과 대조적으로)`를 임의로 삭제 |
| RB-B1 | MDN의 네 항목을 ` / `로 이어 붙임 — 인용이 아니라 편집 |
| RB-B4 | 세 문장 중 가운데를 표시 없이 빼고 이어 붙임 |

앞부분만 맞추는 검사는 뒤를 지어내도 통과시킵니다. **결정: 채택.** Risk 3(품질은 루브릭 저작에서 나온다)의 실물 증거입니다.

### 실험 3 — 진단 호출에서 원문을 빼다 (가장 큰 변경)

| 항목 | 내용 |
| --- | --- |
| 바꾼 변수 | 진단 구조: 1회 호출(루브릭 + 원문 동시) → 2단계 호출(판정은 원문 없이, 교정만 원문) |
| 고정 조건 | qwen3:4b, temperature 0, 동일 입력 |

**되돌림 전 관찰** — 입력: `HTTP는 요청과 응답으로 이루어져 있어요. 요청을 보내면 응답이 옵니다.`

- 필수 6개를 **전부 `이해`** 로 판정. 학습자는 클라이언트도 서버도 한 번도 말하지 않았습니다.
- RB-A1의 "내가 쓴 말"이 **"클라이언트가 보내는 메시지를 요청이라 부르고"** — 이것은 MD-003 **청크의 문장**입니다. 학습자 발화가 아닙니다.
- 오개념 3건 오탐. 전부 같은 발화에 붙었고, 그중 하나는 학습자가 말하지도 않은 "데이터 스트림"을 반박했습니다 (Risk 2 — 없던 오개념 주입).

프롬프트에는 "원문은 판정에 쓰지 마세요"라고 적혀 있었습니다. **지켜지지 않았습니다.**

**적용한 것 두 가지**

1. **구조 분리** — 판정 호출에 원문을 아예 넣지 않습니다. 원문은 모순이 잡혔을 때의 교정 호출에만 들어갑니다.
2. **코드 강제** — 인용이 학습자 발화의 실제 부분 문자열이 아니면 그 판정을 `확인필요`로 내리고 인용을 지웁니다. 오개념도 quote가 학습자 발화에 없으면 버립니다.

**적용 후 관찰**

| 입력 | 유형 | 결과 | 2층 판정 |
| --- | --- | --- | --- |
| 완전한 설명 (클라이언트·서버·방향·시작 주체·순서 모두 언급) | 정답 | 필수 6/6 `이해`, **인용 강등 0건**, 달성 종료 | pass · grounded O cited O complete O |
| `요청과 응답으로 이루어져 있어요…` | 부분 누락 | 인용 검증이 6/6 발동 → 전부 `확인필요` → 되묻기 | pass |
| `React useEffect 어떻게 쓰나요` | 범위 밖 | 0.528 → 거절, 유사도 근거 표시 | pass · **refusal O** |
| `그냥 답 알려주세요` | 정답 요구 | 거절 + 다시 설명 권유, 정답 미노출 | pass · **refusal O** |

**결정: 채택.**

> **부탁으로 지켜지지 않는 경계는 구조로 만듭니다.** 프롬프트에 "쓰지 마세요"라고 적는 것과, 애초에 주지 않는 것은 다릅니다.

**미해결로 남긴 것**: 부분 누락 입력에서 인용 검증이 6/6 발동했습니다. 안전한 방향(`확인필요` → 되묻기)이지만 신호를 잃습니다. `부분`이 맞을 요소까지 보류됩니다. 다음 실험 대상입니다.

### 실험 4 — 종료 조건의 무한 루프 (버그 기록)

| 항목 | 내용 |
| --- | --- |
| 증상 | `Cannot read properties of undefined (reading 'name')` — 힌트가 겨눌 요소가 없음 |
| 원인 | 필수 요소는 전부 `이해`인데 오개념만 남은 경우 `unmet`이 비어 힌트 대상이 `undefined` |
| 함께 발견 | 그 경로에서는 힌트 단계가 오르지 않아 `hintLevel >= 3 && attempts >= 3` 종료 조건이 **영영 성립하지 않음** |

**결정: 채택.** 종료를 재설명 횟수 하나로만 판단하도록 단순화하고, 오개념 전용 분기(`correct`)를 추가했습니다. 조건이 둘이면 한쪽이 오르지 않는 경로에서 종료가 사라집니다.

### 실험 5 — 고정 답변 세트 18건 측정 (PRD 16장)

| 항목 | 내용 |
| --- | --- |
| 고정 세트 | [data/fixed-set.json](data/fixed-set.json) v1.0.0 — 개념 2개 × 9건 |
| 고정 조건 | qwen3:4b, temperature 0, 청크 47개, 구간 0.65/0.58, 루브릭 v1.0.0 |
| 실행 | `npm run measure` · 원자료 [measurement.json](measurement.json) |

측정 하네스는 **앱이 쓰는 모듈을 그대로 불러 씁니다**(esbuild 번들). 프롬프트나 파서를 다시 구현하면 측정 대상이 앱이 아니라 하네스가 됩니다.

#### 세트 구성

| 유형 | 건수 | 무엇을 보는가 |
| --- | --- | --- |
| 완전한 정답 | 2 | 기준선 |
| **표현 변형 정답** | **6** | **FP 전용 셀** — 여기서 오판정이 나오면 다른 지표가 좋아도 출시하지 않는다 |
| 부분 누락 | 4 | 탐지 누락 |
| 오개념 | 4 | 모순 탐지 |
| 범위 밖 | 2 | 거절 |

#### 3차 측정 결과 (최종)

| 지표 | 결과 | 목표 | |
| --- | --- | --- | --- |
| 오판정 FP (표현 변형 정답) | **0건 / 6** | 0건 (상한 제약) | PASS |
| 탐지 누락 (결함을 통과시킴) | **0건 / 8** | 2건 이하 | PASS |
| 오개념 탐지 | **4건 / 4** | 3건 이상 | PASS |
| 범위 밖 거절 | **2건 / 2** | 2건 | PASS |
| 완전한 정답 달성 | **2건 / 2** | 2건 | PASS |
| 판정 일관성 (같은 입력 3회) | **불일치 0 / 16칸** | 측정 후 기준 설정 | — |

**판정 일관성 0/16은 예상 밖의 결과입니다.** PRD 15.2는 4B 모델에서 목표치가 낙관적일 것이라 적었는데, `temperature 0` + `format: "json"` + 구조화된 루브릭 조합에서 요소별 판정이 3회 모두 같았습니다. 다만 표본이 3문항 16칸이므로, 이것을 근거로 목표치를 확정하지는 않습니다.

#### 세 번의 측정 사이에 무엇을 바꿨는가

| | FP | 완전 정답 달성 | 오개념 탐지 | 바꾼 것 |
| --- | --- | --- | --- | --- |
| 1차 | **5 / 6** | 1 / 2 | 4 / 4 | (기준선) |
| 2차 | 1 / 6 | 2 / 2 | 4 / 4 | 오개념 자기모순 검사 추가 |
| 3차 | **0 / 6** | 2 / 2 | 4 / 4 | 모순 대상이 `확인필요`인 경우도 배제 |

**1차의 문제: 오개념 탐지가 사실상 상수였습니다.** 거절되지 않은 16건 중 13건에 오개념이 붙었습니다. 붙은 인용을 보면 원인이 분명합니다.

| 항목 | 오개념으로 잡힌 문장 | 실제 |
| --- | --- | --- |
| B-1 (정답) | "여백은 박스 바깥 공간이라 이 크기 계산에는 들어가지 않아요" | **맞는 말** |
| B-4 (정답) | "width가 가리키는 건 맨 안쪽 내용 층뿐이라" | **맞는 말** |
| H-2 (정답) | "그 기계가 여기 있어요 하고 답을 돌려줘요" | **맞는 말** |

그런데 **같은 진단에서 그 요소들은 전부 `이해`였습니다.** 진단기가 자기 판정과 모순된 것입니다. 이 모순을 검사로 씁니다.

- 오개념에 `contradicts`(어긋나는 루브릭 요소 ID)를 반드시 적게 한다
- 그 요소를 방금 `이해`로 판정했다면 버린다 — 제대로 설명한 요소와 같은 설명이 모순될 수 없다
- 그 요소가 `확인필요`여도 버린다 — **확신하지 못하는 것에 대해 모순을 주장할 수 없다**(원칙 7)

**진짜 오개념 4건은 하나도 잃지 않았습니다.** 모순 대상 요소가 항상 `미도달`이었기 때문입니다 (H-8은 RB-A7, B-8은 RB-B2).

**결정: 채택.** 판정 규칙을 프롬프트에 적는 것과, 모델의 출력을 모델 자신의 다른 출력으로 검사하는 것은 다릅니다.

#### 남은 약점 (숨기지 않습니다)

**① B-2 신호 손실.** 가장 구어적인 정답(CSS 용어를 하나도 쓰지 않음)에서 인용 검증이 2개 요소를 `확인필요`로 내렸습니다. FP는 아니지만, 완전히 맞게 설명한 학습자가 인정 대신 되묻기를 받습니다. 진단기가 학습자 발화를 다듬어 인용한 것이 원인입니다.

**② 과잉 인정 3칸.** 부분 누락 항목에서 비어야 할 요소를 `이해`로 줬습니다 — `H-5/RB-A1`, `H-5/RB-A5`, `H-6/RB-A5`. 셋 다 **RB-A1(클라이언트)과 RB-A5(요청 시작 주체)** 입니다. 학습자가 주체를 말하지 않았는데 문맥으로 채운 경우입니다. 다만 개념 전체가 달성으로 통과하지는 않았습니다(탐지 누락 0).

**③ 표본이 작습니다.** 개념 2개 × 9건입니다. FP 셀은 6건이라 1건이 나오면 곧바로 상한 위반입니다. 이 해상도를 넘는 정밀도를 주장하지 않습니다.

### 실험 6 — 사용자 피드백으로 화면을 걷어내다

첫 사용자가 세 가지를 지적했습니다. 셋 다 맞는 말이라 그대로 적습니다.

| 지적 | 원인 | 고친 것 |
| --- | --- | --- |
| "화면에 정보가 너무 많아서 뭘 눌러야 할지 안 보인다" | 사이드바에 소개·진행·엔진·기록 네 카드. 첫 화면에 `루브릭 v1.0.0`, `필수 요소 6개` 같은 내부 용어 | 이름 한 줄 + 개념 버튼만 남김. 설정·기록은 접음 |
| "그냥 개념만 알고 싶은데 과하게 채점당하는 기분" | **PRD F2의 완화 질문을 구현하지 않음.** 한 줄 입력도 여덟 요소로 채점 | 짧은 첫 입력은 채점하지 않고 되묻기. 첫 화면에 "읽어 보기" 입구 추가 |
| "답을 쓰니까 영어로 줄줄 뜬다" | 힌트 생성에서 qwen3 추론 누출 | 힌트·요약도 `format:"json"` 으로. 스트리밍 폐기 |

**사고 억제 방법 세 가지를 다시 쟀습니다.**

| 방법 | 결과 |
| --- | --- |
| `think: false` | 이 Ollama 빌드가 무시 |
| `/no_think` | **시스템 프롬프트가 있으면 무력화** — 영어 4,135자 |
| `format: "json"` | 사고가 나올 자리 없음 |

실험 1의 결론(`/no_think` 채택)은 **부분적으로 틀렸습니다.** 시스템 프롬프트가 없는 호출에서만 통했습니다. 지우지 않고 여기 남깁니다.

**추가로 잡힌 것 — 같은 인용의 재사용**

`HTTP는 요청과 응답으로 이루어져 있어요…` 입력에서 필수 6개가 전부 `이해`로 통과했습니다. 인용을 열어 보니 다섯 요소가 **"요청을 보내면 응답이 옵니다"** 한 문장을 공유하고 있었습니다. 그 문장에 클라이언트도 서버도 없습니다.

프롬프트 규칙 6에 **이 문장을 예시로 들어** "클라이언트와 서버 요소는 `이해`가 아니다"라고 적어 두었는데도 그대로 했습니다.

→ 한 구간이 3개 이상 요소의 근거로 쓰이면 그 판정들을 `확인필요`로 내립니다. 적용 후 같은 입력이 6/6 → 1/6이 되고 되묻기로 넘어갔습니다.

**되묻는 문장도 모델에게서 뺐습니다.** 맡겼더니 "클라이언트와 서버가 어떤 방식으로 통신하는지…"라며 빠진 요소를 그대로 말했습니다. 힌트 2단계에서야 할 일을 되묻기가 먼저 하면 인출할 것이 남지 않습니다. 고정 문장으로 바꿨습니다.

**자동 판정 배지를 화면에서 뺐습니다.** 사용자가 *"하나라도 빨간불이 뜨면 이 내용 전체에 대한 신뢰도가 없어진다"* 고 했습니다. 맞습니다. 그 판정은 학습자용이 아니라 이 도구가 제대로 판정하는지 재려고 만든 것입니다. **계속 돌리고 기록에는 남기되**(설정과 기록 → 표로 뽑기, `npm run measure`) 학습자 화면에서는 뺐습니다.

**4차 측정 (위 변경 전부 적용 후)** — 전 지표 유지, `B-2`가 미달성에서 달성으로 올라와 표현 변형 정답 6/6이 모두 통과했습니다.

**결정: 채택.** 세 번째로 같은 교훈을 다시 만났습니다 — 프롬프트에 적는 것과 구조로 막는 것은 다릅니다.

### 실험 7 — 두 번째 사용자 피드백

| 지적 | 무엇이었나 | 고친 것 |
| --- | --- | --- |
| "담기 버튼을 없애고 키워드를 써" | 무엇을 왜 담는지 화면에서 알 수 없었다 | 담기 제거. 문단마다 키워드를 세우고, 가리면 키워드만 남게 |
| "CSS 개념을 설명해야지 뭔 퀴즈를 풀라고 해" | 박스 모델 질문이 `왜 300px이 아니라 350px인가`였다 | 개념 질문을 앞세우고 코드는 "막히면 이 예를 보세요"로 접음 |
| "CSS 개념 보러 들어갔더니 아무것도 없다" | **버그** | 아래 |

**버그: 읽기 화면이 통째로 비어 있었다.**

`sourceSummary` 가 청크를 `rubric.title.split(" ")[0]` 으로 찾고 있었습니다. "CSS 박스 모델"의 첫 낱말은 `CSS` 인데 섹션 이름은 `박스 모델 · 여백` 이라 **하나도 걸리지 않았습니다.** HTTP 는 우연히 맞아떨어져 멀쩡해 보였습니다.

**측정이 이걸 놓친 이유**: `npm run measure` 는 진단 경로만 돕니다. `sourceSummary` 는 읽기 화면에서만 쓰이므로 18건 측정을 다 통과하고도 화면 하나가 완전히 비어 있었습니다. **지표가 통과했다는 것이 제품이 동작한다는 뜻은 아닙니다.**

원문 주소로 맞추도록 고쳤습니다. 청크가 어느 문서에서 왔는지는 제목이 아니라 URL 이 말해 줍니다.

**루브릭 v1.0.0 → v1.1.0.** 질문이 개념 서술로 바뀌면서 `RB-B3`·`RB-B4` 의 판정 기준에서 스니펫 숫자 의존을 뺐습니다.

**5차 측정** — 전 지표 통과 유지. **과잉 인정이 3칸 → 1칸**으로 줄었습니다. 질문이 개념을 물으니 답변도 개념을 말하고, 진단기가 문맥으로 채워 넣을 자리가 줄었습니다.

### 실험 8 — 배포 환경에서만 나는 오류

배포본에서 답변을 제출하니 붉은 상자에 **`Failed to fetch`** 만 떴습니다.

**원인**: `OLLAMA_ORIGINS` 미설정. 실측했습니다.

| 시험 | 결과 |
| --- | --- |
| 배포 출처 → 설정 안 한 Ollama (preflight) | **403 Forbidden** |
| 배포 출처 → `OLLAMA_ORIGINS` 준 Ollama | **204**, `Access-Control-Allow-Origin` 정상 |

로컬 개발 주소는 Ollama가 기본으로 허용하기 때문에, **로컬에서는 끝까지 잘 되다가 배포에서만 깨집니다.** README에 적어만 두고 실제로 이 경로를 밟아 보지 않아 발견이 늦었습니다.

**진짜 결함은 오류 메시지였습니다.** `Failed to fetch` 는 사용자가 할 수 있는 일이 하나도 없는 문장입니다. 게다가 브라우저는 **CORS 차단과 서버 꺼짐을 똑같은 문구로** 돌려주는데, 둘은 사용자가 할 일이 완전히 다릅니다.

`mode: "no-cors"` 로 한 번 더 두드려 보면 갈립니다. 서버가 살아 있으면 불투명 응답이 돌아오고, 꺼져 있으면 그때는 진짜로 던집니다.

| 상황 | 일반 fetch | 판별 |
| --- | --- | --- |
| 살아있고 CORS 허용 | ok | — |
| 살아있지만 CORS 거부 | `Failed to fetch` | **cors** |
| 포트가 죽음 | `Failed to fetch` | **down** |

이제 상황에 맞는 안내가 나옵니다. CORS면 **현재 페이지 주소를 넣은 `setx` 명령을 그대로** 보여 주고, 꺼짐이면 Ollama 실행과 `ollama pull` 을 안내합니다.

**세 번째 원인이 있습니다 — 브라우저가 아예 막는 경우.**

배포 후 실제 https 주소에서 다시 재 봤습니다.

| 배포 페이지에서 보낸 요청 | 결과 |
| --- | --- |
| 공개 https 사이트 | ok |
| 같은 출처 자산 | ok |
| `localhost:11434` · `127.0.0.1:11434` | **차단** (`net::ERR_BLOCKED_BY_CLIENT`) |

CORS 나 Private Network Access 가 아니라, **그 브라우저가 원격 페이지에서 루프백 주소로 가는 요청을 정책으로 막는** 것입니다. 확장 프로그램이 막는 경우도 같은 오류를 냅니다.

이 경우 `mode:"no-cors"` 두드리기도 실패하므로 앱은 `down` 으로 판단합니다. Ollama 를 켜 둔 사람에게 "꺼져 있어요"라고 말하면 고칠 방법을 찾을 수 없으므로, **https 페이지에서의 `down` 안내에 두 가능성을 함께 적었습니다.**

**여전히 미확인**: Ollama 응답에 `Access-Control-Allow-Private-Network` 헤더가 없습니다. PNA 를 강제하는 브라우저에서 어떻게 되는지는 확인하지 못했습니다. 위 차단이 먼저 걸려 그 뒤를 볼 수 없었습니다. **추정으로 적지 않습니다.**

**결정: 채택.** 문서에 적어 두는 것과 그 경로를 실제로 밟아 보는 것은 다릅니다.

### 실험 9 — 과제 요구 대비 자체 감사

UI 를 여러 번 걷어내면서 **과제 요구까지 같이 지운 것**이 있는지 코드를 훑었습니다. 일곱 개가 나왔고 전부 되살렸습니다.

| 요구 | 무엇이 문제였나 | 어떻게 되살렸나 |
| --- | --- | --- |
| 출처 공개 | 답변 화면에 근거를 볼 방법이 **아예 없었음** | `이 답이 본 자료 N개` 접힌 줄. 펼치면 ID·섹션·유사도·원문 링크 |
| 자동 판정 표시 | 화면에서 뺐고 기록에만 있었음 | `이 진단 자체 검사 · 믿을 만해요` 접힌 줄. 영어 필드명 대신 질문 형태로 |
| 사람 피드백 | 👍👎 **UI 가 삭제되어 있었음** | 답변 끝에 두 개. 자동 판정과 같은 줄에 기록 |
| 스트리밍 | 전부 논스트리밍 | 아래 참고 |
| 첫 방문 진행률 | `설정과 기록` **접힌 상자 안**. 200MB 받는 동안 첫 사용자는 아무것도 못 봄 | 받는 중일 때만 밖으로 나오는 카드 |
| 프롬프트의 URL·섹션 | `[MD-001] 본문` 뿐. **url·section 이 안 실림** | `evidenceBlock()` 한곳에서 `[ID] (섹션 · URL)` 형식으로 |
| PRD 화면 구성 | 절 자체가 **없었음** | PRD 8-A 신규 |

**스트리밍 — 양립 불가인 줄 알았던 것**

사고 누출을 막는 유일하게 확실한 방법이 `format:"json"` 인데, 그러면 흘러나오는 것이 JSON 이라 그대로 보여 줄 수 없었습니다. 그래서 스트리밍을 포기했었습니다.

다른 길도 재 봤습니다. `think:true` 로 보내면 Ollama 가 사고를 `thinking` 필드로 분리해 줍니다(실측 13,167자). 깨끗하지만 **두 문장짜리 힌트에 13,000자를 생각한 뒤에야 답이 시작**되어 더 나쁩니다.

세 번째 길이 있었습니다. **흘러나오는 JSON 에서 값만 실시간으로 뽑으면** 됩니다.

```
{"hint": "요청을 보내는     →  요청을 보내는
{"hint": "요청을 보내는 쪽은 말씀하  →  요청을 보내는 쪽은 말씀하
```

사고가 나올 자리가 없으면서 글자가 차오르는 것이 보이고, 속도도 그대로입니다. 조각 단위로 시험해 정확히 뽑히는 것을 확인했습니다.

**6차 측정** — 전 지표 통과 유지. 프롬프트에 URL·섹션이 늘었는데도 판정이 흔들리지 않았습니다(일관성 0/16).

**남은 것**: 배포 주소에서 PRD 14장 수용 기준을 직접 돌려 보는 일. 제 브라우저가 원격 페이지의 `localhost` 호출을 막아 확인하지 못했습니다.

## 알려진 한계

- **진단 품질은 사용자가 고른 로컬 모델에 달려 있습니다.** `qwen3:4b`에서 인용 조작이 관찰되었고, 코드로 막았지만 그 대가로 판정이 자주 보류됩니다.
- **판정 일관성은 아직 측정하지 않았습니다.** temperature 0에서도 같은 입력의 진단이 실행마다 달라집니다. PRD 15.2에 따라 1차 측정 후 목표를 확정합니다.
- 2층 판정도 LLM이 합니다. 판정 자체가 틀릴 수 있습니다.
- 오개념 목록은 아직 **추정**입니다. 실제 학습자 답변으로 교체해야 합니다 (PRD 6.4).
- 첫 로드가 무겁습니다 (임베딩 모델 약 200MB + ONNX 런타임 WASM).
- 루브릭 저작에 개념당 수 시간이 듭니다. 이것이 개념 확장의 실제 제약입니다.
